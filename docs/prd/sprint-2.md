# PRD — Sprint 2

# Title

Input Engine

---

# Objective

Establish a continuous stream of input events from the selected mouse device.

At the end of this sprint, MouseFlow should continuously receive and display raw input events generated by the device selected during the previous sprint.

This sprint focuses exclusively on event acquisition.

No event interpretation or action execution is performed.

---

# Problem

After identifying the correct mouse device, MouseFlow must continuously receive user interactions.

Without a reliable event stream, the application cannot react to button presses, wheel movements, or future gestures.

The input engine becomes the foundation for every subsequent feature.

---

# User Story

As a Linux user,

I want MouseFlow to detect my mouse interactions in real time,

so that future versions of the application can respond to them.

---

# Success Criteria

Once the application starts:

- it begins listening for input events from the selected device;
- supported events are displayed as they occur;
- events are processed continuously;
- the application remains active until interrupted by the user.

---

# Scope

This sprint includes:

- opening the selected input device;
- continuously receiving input events;
- displaying supported events;
- graceful application shutdown.

---

# Out of Scope

This sprint does not include:

- window detection;
- event routing;
- configuration loading;
- action execution;
- gesture recognition;
- event filtering beyond supported event types.

---

# Functional Requirements

## Event Stream

The application shall establish a continuous stream of input events from the selected device.

---

## Supported Events

The application shall recognize and report supported mouse events.

Initial supported events include:

- BTN_SIDE
- BTN_EXTRA
- BTN_FORWARD
- REL_HWHEEL

Additional event types may be introduced in future sprints.

---

## Continuous Execution

The application shall continue processing events until interrupted.

---

## User Feedback

Each supported event shall be displayed immediately after it is received.

Example:

```text
BTN_SIDE

BTN_EXTRA

REL_HWHEEL
```

---

## Graceful Shutdown

When interrupted by the user, the application shall terminate cleanly without leaving resources open.

---

# Non-functional Requirements

The solution should:

- process events with minimal latency;
- avoid unnecessary CPU usage;
- provide deterministic behavior;
- support long-running execution.

---

# Design Principles

This sprint should prioritize:

- continuous execution;
- reliability;
- simplicity;
- low latency;
- clean resource management.

---

# Acceptance Criteria

The sprint is complete when:

- input events are received continuously;
- supported events are displayed in real time;
- unsupported events do not interrupt execution;
- the application remains responsive while idle;
- the application exits cleanly when interrupted.

---

# Risks

Potential challenges include:

- unexpected device disconnections;
- unsupported event types;
- long-running resource management;
- interruption handling.

These risks should not compromise application stability.

---

# Future Work

The next sprint will identify the currently focused application, allowing input events to be associated with a specific window.
